# 实时数据改走同源聚合层 —— 前端迁移说明

> 目标：前端不再直连 agent（不再拼 `machineUrl`），改为调用 group-center 同源端点。收益：去 CORS、去拓扑暴露、N 个页面共享一份 5s TTL 快照。状态：前端**全量迁移已完成**，`tsc --noEmit` 零错误；后端 task 字段**已补齐**（15 → 36，见第 5 节）。

---

## 1. 端点迁移映射

| 旧（直连 agent） | 新（同源） | 说明 |
| --- | --- | --- |
| `GET /web/open/front_end/publicMachineList` | `GET /web/open/realtime/machines` | 多出 `serverNameEng` / `agentOnline` / `stale` |
| `machineUrl`（`/gpu/3090`）拼 agent 域名 | `serverNameEng`（`3090`）作路径参数 | 旧 key 恰好是新 key 的最后一段，**老链接行为不变** |
| `gpu_count` + 逐卡 `gpu_usage_info?gpuIndex=N` + `gpu_task_info?gpuIndex=N` | 一次 `GET /web/open/realtime/machines/{name}/gpu` | 8 卡从 17 请求降到 1 请求 |
| `disk_usage` + `system_info` | 一次 `GET /web/open/realtime/machines/{name}/disk` | 系统内存挂在这里的 `system` 字段 |

三个端点都在 `/web/open/**` 下，无需鉴权，返回统一信封 `ClientResponse`，业务数据在 `result` 里。

### 请求量对比（8 卡机器 / 单个观看者）

|  | 旧 | 新 |
| --- | --- | --- |
| 每 2s | `gpu_usage_info` ×2 + `gpu_task_info` ×1（**每卡**）→ 约 12 req/s | `/gpu` ×1 → 0.5 req/s |
| 每 5s | `system_info` ×1（**每卡**，结果从未被使用——死轮询） | 已删除 |

## 3. spec 之外实测发现的三个关键点

### 3.1 错误路径是 HTTP 200 + `isSucceed: true`

```jsonc
// GET /machines/nonexistent/gpu
{
  "isSucceed": true,
  "haveError": false,
  "result": {
    "source": "none",
    "error": "unknown machine: nonexistent",
    "snapshot": [],
    "gpuCount": 0,
    "stale": true,
    "freshness": -1,
    "snapshotTime": 0,
  },
}
```

**不能用 `isSucceed` 或 HTTP 状态码判断有无数据，必须判 `source === 'none'`。** 否则「机器不可达」会被渲染成「一台 0 张卡的正常机器」——看起来正常，实则骗人。

前端实现：`components/Machine/Realtime/snapshotEmptyState.ts` 统一收口四条降级路径 + 两种前端失败情况，返回空态文案；各页面不再各自判断。

### 3.2 `agentOnline` 与数据可用性完全解耦

实测所有真实响应里 `agentOnline` 都是 `false`，但 `source:'agent'`、`freshness:0`，**数据是活的**。如果拿 `agentOnline` 去 gate 数据显示，会把正常机器全部判成离线。

前端实现：只做独立的在线圆点（`RealtimeStatusBadge` 的 `showAgentDot`），不参与数据放行。

### 3.3 系统内存从 `/gpu` 挪到了 `/disk`

旧 `system_info` 在 GPU 看板用于内存 tooltip，新结构下 `system` 挂在 `/disk` 响应里。 **GPU 看板要显示内存，必须同时轮询 `/gpu` 和 `/disk`。**

已确认旧 `system_info` 的 `cpuModel`/`osName`/`uptime` 等字段全仓从未被渲染，新 `system` 的 4 个内存字段刚好够用，无功能损失。

### 3.4 迁移后必须删掉 proxy 里的 `/gpu` 规则（否则 GPU 看板 404）

`config/config.proxy.ts` 原本有一条：

```js
'/gpu': { target: GROUP_CENTER_URL + '/gpu/', pathRewrite: { '^/gpu': '' } }
```

它服务于旧架构「前端直连 agent」（`machineUrl` 形如 `/gpu/3090`）。迁移到同源聚合层后前端不再直连 agent，**这条规则已无用**，但它的前缀匹配会连前端自己的路由一起吃掉：

```
GET /gpu-dashboard  →  被转发到后端
→ No static resource gpu/-dashboard  → 404
```

**实测现象**：磁盘看板正常，只有 GPU 看板 404（mock 模式下因为 mock 中间件优先级高于 proxy 而掩盖了这个问题，`npm run dev:proxy` 才会暴露）。

已删除该规则。这是「前端不再需要知道 agent 拓扑」这一收益的直接体现。

#### 4.1 多卡配色的降级处理

新 task 没有 `topPythonPid`，原本按它分组给同一个 DDP 任务配色会退化成所有多卡任务共用一个颜色。已改为三级回退（`getTaskGroupKey`）：

```
topPythonPid  →  screenSessionName  →  projectName/pyFileName
```

优先级最高的仍是最可靠的 `topPythonPid`，后端补齐后自动切回，无需改调用方。

顺带修了一个旧 bug：`colorSelectNewColor` 原本绕过去重逻辑直接从原数组取色，会让两个不同任务撞色。

#### 4.2 详情抽屉的空值保护

`GpuTaskDetailTags.tsx:37` 原写法 `cudaVersion.split('.')` 在字段缺失时是**硬崩溃**（会把整个弹窗带崩，与之前修过的 `userEnvEpoch.length` 同类）。已统一走 `utils/format.ts` 的 `shortenVersion()` 做空值保护。

## 5. ✅ 后端字段已补齐（15 → 36）

> **2026-09-10 更新：本节所述缺口已修复。** 原「待补 22 个字段」现已全部透出，实测 `/machines/3090/gpu` 的 `task` 字段数由 **15 升至 36**。

### 5.1 归因：缺口 100% 在后端，agent 无辜

实测 `curl http://g.329509.xyz/gpu/3090/gpu_task_info?gpuIndex=0` —— **agent 返回全部 36 个字段**， `zero*` 告警全套、`torch*`、`cudaRoot`、`driverVersion`、`multiprocessingSpawn` 一个不少。字段是在后端被丢掉两次：

| 断点 | 位置 | 丢弃原因 | 数量 |
| --- | --- | --- | --- |
| ① DTO 未声明 | `datatype/agent/AgentResponses.kt` 的 `AgentGpuTaskItem` | `NviNotifyAgentClient` 配了 `FAIL_ON_UNKNOWN_PROPERTIES=false`，**未声明字段被 Jackson 静默丢弃**（连日志都没有） | 14 |
| ② 映射未写入 | `RealtimeSnapshotService.toTaskBrief` | 字段**已解析进内存**，却没写进 `GpuTaskBrief` —— 纯白丢 | 7 |

### 5.2 后端改动（3 个文件，纯透传）

| 文件 | 改动 |
| --- | --- |
| `datatype/agent/AgentResponses.kt` | `AgentGpuTaskItem` 补齐 14 个字段；`id` 由 `Long` 改为 `String` |
| `datatype/realtime/RealtimeModels.kt` | `GpuTaskBrief` 补齐 21 个字段 |
| `service/RealtimeSnapshotService.kt` | `toTaskBrief` 补齐映射；`id` 用 `toLongOrNull() ?: 0` 安全转换 |

**前端零改动即成**：`RealtimeGpuTask` 早已声明全部 37 个字段并做了可选 + `VShow` 保护。

### 5.3 两个必须知道的坑

1. **`topPythonPid` 实测返回 `-1`**，语义是「无法判定主进程 PID」，不是 0 也不缺失。前端 `getTaskGroupKey`（`topPythonPid > 0`）与详情页 `VShow` 均已正确处理，因此后端**保持原样透传**。⚠️ 不要"顺手"把它改成 `null` —— 前端类型是 `number`，会引入 `null`。
2. **`id` 在 agent 侧是字符串** `"20260902044750"`。后端用 `String` 接收、`Long` 输出，解析失败退化为 `0`；前端据此把订阅入口置灰，**避免把 `0` 当合法 `projectId` 传出去**。这样即使 agent 将来返回非数字 ID，也只是订阅入口不可用，而不会因解析异常**丢掉整个 taskList**。

## 6. 本地运行

### 6.1 启动后端（关键）

**机器清单不来自数据库**，来自后端项目的 `Config/Machine/real.yaml`（本地私有、已 gitignore）；GPU / 磁盘实时数据则由后端 pull 生产 agent 入口（把 `/gpu/{nameEng}/*` 转发到内网 agent）。两者都由环境变量指定，缺一个就看不到数据：

| 环境变量 | 值 | 缺失后果 |
| --- | --- | --- |
| `CONFIG_MACHINE_PATH` | `./Config/Machine/real.yaml` | `/machines` 返回空数组 `[]` |
| `REALTIME_AGENT_BASE_URL` | `http://g.329509.xyz` | 三个端点全部 `source:"none"`。机器配置里 `apiUrl` 是相对路径（`/gpu/3090`），后端靠该前缀拼绝对地址 |
| `SPRING_DATASOURCE_URL` | `jdbc:mysql://172.22.22.1:3306/group_center?...` | 数据源初始化失败 |

> 注意：`ConfigEnvironment` 读到的 `FileEnv.toml` 只进它自己的 map，**不会同步给 Spring**，所以上面三项必须用系统环境变量传入。IDEA 的 bootRun 配置只传了 `FILE_ENV_PATH`，不够用。

后端项目已提供一键脚本（文件名含 `.local`，被根 `.gitignore` 的 `*.local*` 忽略，不入库）：

```bash
cd /Users/yves/code/web/group-center
./run.local.sh
```

启动成功判断：`lsof -nP -iTCP:15090 -sTCP:LISTEN` 有输出，日志出现 `Tomcat started on port 15090`。
